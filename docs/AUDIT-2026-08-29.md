# Platform audit — 2026-08-29

Eight parallel auditors over `core/` (28k lines), `web/` (72k), `db/` (11.5k,
129 migrations) and `ml/` (2.7k), plus one lens no code-reader has: what
production actually did over the preceding days.

**Every finding below was verified independently before it was written down** —
against the live catalogue, the live database, a probe, or the built output.
Where a claim did not survive verification it is recorded as corrected, not
quietly dropped: an unverified red sends someone to fix code that is not broken,
which is the more expensive failure.

Health at the time of audit: no run stuck over an hour, every queue empty, all
calls in a settled state, 1,196 core tests and 664 web tests green, the db wall
suite 44/44 (641 checks).

## Part 1 — Security

### S1 · CRITICAL — any org admin can permanently become the owner

`core/src/api/server.ts:2877` · `core/src/api/apikeys.ts:222`

`POST /v1/gateway/keys` takes `actor_id` from the request body. `mint()` calls
`assertUuid` on it — validating the *shape*, never that it is the caller — and
the only other bound is db/0009's composite FK, which requires the same org and
nothing else. `resolveIdentity` later reads that actor's real role from
`app_user`, so a key minted with the owner's id **carries owner authority**, and
keys are immutable.

*Attack:* an admin reads `GET /v1/admin/members`, finds the owner's uuid, mints a
key naming it, and holds owner authority forever.

*Verified:* read the route, `mint()`, and `resolveIdentity`'s `role: row.role`;
the auditor's live probe showed the same admin's key answering `403` as a member
and `204/200` on owner-only routes as the owner.

*Why it survived:* every other owner boundary is enforced — `members.update`
refuses `role=owner`, invitations refuse inviting an owner. This is the one door
left open, and it is the door that mints credentials.

**Fix:** refuse `actor_id !== identity.userId` unless the caller is the owner;
or drop the parameter and always mint for the caller.

### S2 · CRITICAL — 134 of 161 routes accept a gateway key, including the surfaces the product promises are private *from admins*

`refuseApiKey` exists (`server.ts:1996`) and is applied to 19 routes.

Reachable with a key today, verified by live injection: assistant conversations
and their messages (M15 says private even from admins), mail draft bodies and the
real inbox message behind them (M43 says not even an admin sees a draft),
connector listings and `DELETE /v1/connectors/google` (D29: an admin governs the
org, not a colleague's mailbox), the device/IP list, `DELETE /v1/me/voiceprint`,
profile writes, and thread sharing.

Combined with S1, "a key acts as its owner" becomes "a key acts as anyone an
admin chooses". The mail-drafts block comment claims a key cannot reach it —
true of `send`/`discard`, false of `list` and `source` two lines above.

**Fix:** invert the default. `refuseApiKey` on everything, with an explicit
allow-list of machine-safe routes, asserted by the existing auth-coverage test.

### S3 · HIGH — the agent can execute a DELETE

`db/migrations/0095_delete_summary_version.sql:61`

`delete_summary_version` is the only SECURITY DEFINER function in 129 migrations
with no `revoke all … from public`, so PUBLIC keeps EXECUTE — and PUBLIC
includes `echo_agent`. Its internal guard is "owns the call", and the agent
**runs as the call's owner**, so the guard is satisfied by construction.

*Verified against the live catalogue:* `proacl = {=X/postgres, …}` (the leading
`=` is PUBLIC); of 72 definer doors the agent may execute 14, and this is the
only DELETE-bearing one — the probe discriminates.

This breaks M3/D3's absolute: *the agent's role has no DELETE anywhere*. No
agent path calls it today; the wall exists for the day one does.

**Fix:** one `revoke all on function … from public`, plus S8's instrument.

### S4 · HIGH — six definer doors mutate any org's rows with no caller check

`set_mail_cursor` (0119:46), `claim_mail_poll` (0114:148), `claim_meeting_poll`
(0117:91), `claim_workflow_fire` (0111:26), `mark_agent_rule_fired` (0074:121),
`close_stale_auth_sessions` (0126:56).

All run as `postgres` (which bypasses RLS), all are executable by `echo_app`, and
**none reads `echo.actor_id()`** — verified live: `checks_caller = false` on all
six. `set_mail_cursor` is sharpest: it writes an attacker-chosen cursor onto any
connection on the platform, permanently suppressing another org member's mail
drafting. `close_stale_auth_sessions` signs out every user idle ≥3 days.

The negative control is one file away: `workflow_graph_for_run` (0107:27) *does*
carry `and r.owner_id = echo.actor_id()`. The pattern is established; these
skipped it. Only worker code calls them today — but the wall's stated job is to
hold when the layer above fails.

### S5 · HIGH — an org admin can mint a second owner by INSERT, with no status history

`db/migrations/0013_rls_policies.sql:81`

`app_user_admin_insert`'s WITH CHECK constrains org and admin-ness, but places no
predicate on `role` or `status`. The guard that forbids exactly this
(`app_user_guard`) is **BEFORE UPDATE only**, and no CHECK constraint restricts
`role`. Because the trigger is UPDATE-only, `record_status_change` never fires
either — the new active owner appears with no history line.

Reachability is limited (core inserts into `app_user` nowhere; every creation goes
through a definer door, and the FK requires a real `auth.users` id), which is why
this ranks below S1.

### S6 · MEDIUM — the live-STT ticket rides the query string into the logs

`server.ts:1058,1078` · `main.ts:30`

`?ticket=` is the entire authority for pushing audio and reading captions, both
routes serve `access-control-allow-origin: *`, and pino's redact list contains
`"url"`, which does not match Fastify's `req.url`. Verified by capturing stdout:
the ticket appears verbatim in the request log. Captions are content (invariant 7).

**Fix:** move it to a header, or redact `req.url`.

### S7 · MEDIUM — one org's admin controls sign-in for every tenant

`0078_signin_methods.sql` · `server.ts:326`

`signin_method` is platform-scoped with no `org_id`; `set_signin_method` gates on
`actor_is_admin()` alone. The migration named this seam honestly and conditioned
it on "today's single-org platform" — a precondition M32 has since made untrue.
Any tenant's admin can disable Google/GitHub sign-in for all tenants. Wants
`require_platform_root`.

### S8 · MEDIUM — the delete-wall instruments are structurally blind to S3

`db/test/30_agent_wall.sql:38`, `50_identity_search_gateway.sql:28`

Both assert the delete wall through `information_schema.role_table_grants`. A
definer function that deletes is invisible to that view — so "the agent holds no
DELETE grant on any table" is true, and "the agent deletes nothing" is not.

**Fix:** assert over `pg_proc` — every SECURITY DEFINER function in `echo` must
carry an explicit non-PUBLIC ACL — and verify it red by staging one omission.

### S9 · LOW, verified

- `CORE_URL` reaches the browser in an upstream-failure message (`web/src/server/core.ts:124,221`).
- `GET /v1/org/logo` lacks `X-Content-Type-Options: nosniff`.
- ~50 BFF route files interpolate path segments without `encodeURIComponent`.
- Outgoing mail headers are built from provider-authored values with no CRLF
  strip (`connectors.ts:346`); the subject is safe only by accident, because its
  ASCII test happens to fail on CR/LF. Whether a bare CRLF survives Gmail's
  normalisation is unproven — the code has no defence either way.
- JWT **audience pinning is implemented and unreachable**: `audience` is not a
  field on `AuthOptions`, so no caller can pass it, despite the file's comment
  saying it is what stops an anon-key token being accepted. `SUPABASE_JWT_ISSUER`
  appears in no deploy script.

### Checked and clean (security)

All 44 `echo` tables have RLS enabled **and forced**; 0 of 101 policies granted
to `public`; every policy override traced across 129 migrations is equal-or-narrower
than what it replaced; `echo_agent` holds zero DELETE table grants and `ar` only
on `mail_draft` (M43's grant-is-the-wall holds); its column reach excludes email,
username and preferred_model; `echo_app` holds exactly one DELETE (`call_note`,
the ratified D3 exception); the 15 platform-root routes all verify
`p_actor = actor_id()`; SSRF guards are complete including rebinding and per-hop
redirect re-checks; OAuth uses PKCE end to end with tokens AES-256-GCM at rest;
no `console.*` in core; pg errors logged by structured field only; zero SQL
interpolation anywhere except the two-value `SET LOCAL role` literal.

## Part 2 — Correctness

### C1 · CRITICAL — webhook deliveries are enqueued and never consumed

`core/src/worker/main.ts` · `webhook-step.ts:61`

The worker never mounts the dispatcher. `main.ts` contains **no occurrence of
"webhook"**, and `git log -S "createWebhookStep" -- core/src/worker/main.ts`
returns nothing — it was never wired, in any commit. `createWebhookStep`'s only
non-test importer is an e2e file.

Every delivery enqueues, the row stays `delivered_at=null, failed_at=null`, the
UI renders it *pending* forever, and the pgmq queue grows without bound. **Zero
webhooks have ever been delivered.**

Found independently by two auditors. Rule 13½'s exact shape — and the reason it
survived is that the repo's producer-with-no-consumer instruments cover db
functions, routes and tables, and have **no queue sibling**.

*Next behind it:* a delivery marked "retrying" is never retried — `settle()`
writes `next_attempt_at` and returns normally, so the message is removed and
nothing reads that column.

### C2 · HIGH — the no-Claude rule's fourth failure

`core/src/api/server.ts:535`

`POST /v1/calls/:id/translate` takes `body.model` as free text with **no
`assertAskable`** — verified: five routes call it (361, 1923, 1952, 3065, 3247)
and translate is not one of them — and its fallback reads `me().preferred_model`
**raw**, not through `servablePreference` the way `models.list` and
`models.preferred` do. Nothing downstream re-checks.

A billed run routes to an excluded model either by asking for it by name, or
silently from a stale stored preference.

### C3 · HIGH — a retry writes another real draft into the person's mailbox

`core/src/api/mail-drafts.ts:130-166`

`connectors.createDraft()` writes to Gmail at line 133; the row insert is at 148.
The docstring claims idempotency by the unique constraint — but **the conflict
fires after the second reply is already in the mailbox**. The unique protects our
row, not the user's Drafts folder. `applyDraftMail` lets the ConflictError escape;
the runner classifies unknown errors as retryable by design; so each retry adds
another draft, then dead-letters.

*Verified by probe:* driving the step twice with a ledger row still `running`
produced **2 drafts**.

### C4 · HIGH — a workflow `apply` re-runs its effect on redelivery

`core/src/worker/workflow-step.ts:1230`

Redelivery adoption covers ledger rows marked `done` and `skipped`. A row still
`running` — the crash window between the effect and its status update — falls
through and executes again. db/0104:178 asserts "the worst redelivery outcome is
wasted work, never a doubled effect"; `step_once` protects the *row*, not the
*effect*.

*Why no test caught it:* `scenario()` in `workflow-step.test.ts:110` defaults every
ledger row to `running`, so every existing test **is** that path and none
distinguishes attempt 1 from attempt 2.

### C5 · HIGH — the platform user patch erases fields it was not given

`db/migrations/0069:85-86`

`display_name` uses `coalesce(…, display_name)` — correct. The two lines under it
use `nullif(btrim(coalesce(p_x, '')), '')` — an **unconditional overwrite**. The
line beneath them is correct again. So `PATCH /v1/platform/users/:id {"role":…}`
silently wipes that person's `username` and `display_name_en`, and a freed handle
can be re-worn — against M24's reservation rule.

Invisible today only because the web form happens to round-trip all five fields.

### C6 · HIGH — two parts of one call each queue the next stage

`core/src/worker/steps.ts:275`

`finishPart` is check-then-act with no claim and no constraint, and worker
concurrency defaults to 2. *Verified by probe:* two concurrent handlers →
**2 `link_speakers` messages** → two summarize runs → two model-paid summaries →
a duplicated `call.transcribed` fan-out. And `summarize` itself is not idempotent
(`call-steps.ts:336`): a redelivery re-pays the model and appends another version.

### C7 · HIGH — a status flip commits without its queue message, and nothing sweeps the result

`api/uploads.ts:647,576` · `api/workflow-runs.ts:91` · `worker/workflow-triggers.ts:44`

`queue.send` opens its own transaction, so the status write and the message can
never be atomic as written. One failed enqueue strands a call at `summarizing`
forever — and **both recovery doors then refuse it**: retry demands `failed`,
resummarize demands `ready`.

The engine even has a name for this state: `"stalled"` is in
`WORKFLOW_FAILURE_CODES` with **zero producers** in core.

### C8 · MEDIUM — verified, in brief

- **`enqueueConnectorEvent` reports `false` after already starting a run**
  (`workflow-triggers.ts:142`) — the catch discards a `fired` flag a prior
  iteration set, so the poller *also* drafts. Two replies to one email. Proven by
  probe. It is exactly what the function's own comment says must not happen.
- **`foreach → propose → wait → apply` applies only iteration 0**
  (`workflow-step.ts:838` pins `iteration = 0` while `wait` requires *all*
  decided). Ten approved writes, one performed, nine vanish with no error.
- **Call status can move backwards** — `setCallStatus` is an unguarded UPDATE, so
  a redelivery sets a `ready` call back to `summarizing`.
- **A meeting can be marked handled with no brief** (`meeting-prep.ts:237`) — the
  mark lands before the enqueue and ignores its result; the fallback is then
  silenced permanently.
- **`sessions.append` documents a race protection it does not have**
  (`sessions.ts:344`) — `max(seq)+1` under READ COMMITTED, no `on conflict`, and
  23505 is unmapped, so two tabs produce a **500**.
- **The mail poller abandons mail silently** (`mail-poll.ts:343`) — the cursor
  advances past everything while the per-sweep cap drafts only the newest few;
  the remainder is never examined and nothing is logged (M21: forfeits are loud).
- **ml/'s positive-detection warnings are dropped** — `warnings` has two type
  declarations in core and **zero reads**, so "VAD found no speech" reaches nobody.
- **A malformed id becomes our 500** — `22P02` has no branch anywhere; the route
  layer never calls the existing `assertUuid`. Confirmed in production: 7 internal
  errors in 3 days, all `string_to_uuid`, across four endpoints.
- **Provider 402 is classified nowhere** — all 23 failed assistant runs (of 336)
  were OpenRouter "requires more credits", Aug 19–21. Users saw a broken
  assistant; no admin was told the workspace was out of credit.
- **Two wire fields typed `string` are `Date` at runtime** (`transcripts.ts:392`,
  `calls.ts:632`) — and the covering fixture hands the mapper a *string*, so the
  test agrees with the code and cannot fail (rule 9).
- **Call-list paging drops ties** — `started_at < $2` with no id tiebreaker, while
  the audit feed in the same repo does it correctly with a full row comparison.
- **The platform console's search silently stops filtering** — unescaped `%`/`_`,
  where `members.ts:913` has the fix with the reason written out.
- **The org audit reports "nothing changed" for six real fields** — `changedFields`
  is a hand-maintained list that omits every profile field.

### C10 · Frontend — the shipped product

**F1 · CRITICAL — resuming an interrupted recording white-screens the app.**
`web/src/components/echo/Recorder.tsx:289` returns early when the resume target is
still loading, and **four hooks live below that return** (lines 431, 474, 475).
The first render runs them all; the moment `?resume=` sets the loading state React
sees fewer hooks and throws. Verified by reading the file and by the auditor's
probe: `Rendered fewer hooks than expected`. Both entry points — the unfinished-
takes card and the records row action — are dead. `Recorder.discard.test.tsx`
never sets the query param.

**F2 · HIGH — the propose→approve gate does not exist in the shipped product.**
Core emits the `proposal` stream event and web declares its type — but neither
live reducer (`Hub.tsx:539`, `PresenceDock.tsx:870`) has a `case "proposal"`;
Hub's "unknown event types are ignorable by contract" silently swallows it. The
only handler lives in `AssistantPane.tsx`, which **nothing imports**, and
`client.ts:1944`'s `decideProposal` is still a Phase-A fixture that voids its
arguments and returns `"ok"` after 180 ms. So: the assistant proposes a write, no
approve control renders, the write never happens — and a re-mounted card would
report success and write nothing.

**F3 · HIGH — the per-meeting summary-model picker is inert.** The BFF rebuilds
the create-call body from six named keys and `summary_model` is not one of them,
though core reads it (and even `assertAskable`s it). Verified: exactly two
non-test mentions in web, neither in the BFF. The picker shows a checkmark and
changes nothing — the same shape as the org-form incident of 2026-08-26.

**F4 · HIGH — the workflow builder publishes over a graph it failed to load.**
If `workflowGraph()` rejects, the catch is empty and `steps` stays `[]`; Save then
publishes that as a new version and repoints `current_version_id`. Core refuses a
*zero*-step graph, so the degenerate case is caught and the realistic one is not:
one transient 500 plus one save reduces an admin's workflow to a single step, and
no web surface consumes the versions endpoint, so there is no in-product rollback.

**F5 · HIGH — a call's page conflates loading, failed, forbidden and absent.**
Four fetches with no `.catch` and a render gate of `if (!call) return null` —
any failure is a permanently blank page under the shell, indistinguishable from
loading, plus four unhandled rejections. The same effect has no request-id guard
and deps of `[id]`, so navigating between two calls lets the first one's
responses land on the second one's page.

**F6 · HIGH — the wake word is silently deaf without an undocumented env.**
`voiceLoop.ts:382` always posts audio to `${base}/v1/live-stt/...`; with
`CORE_PUBLIC_URL` unset, `base` is `""` and the path resolves to a Next route
that does not exist. `fetch` gets a 404, so the catch never fires. The env appears
nowhere else in the repo — no example file, no deploy doc — and the BFF's own
comment promises that without it "everything still rides the BFF paths".

**F7 · MEDIUM, verified** — recorded part blobs are never revoked (up to 45 MB per
part retained for the page's life); the leave-prompt detaches *before* uploads
drain, so closing the tab mid-upload loses parts silently; `startVoiceLoop` can
install a live microphone after the caller asked for silence (three reachable
windows, one of which is during a recording); a pending consent card wedges the
dock permanently because its promise has no rejection path; the workflow run page
reports every failure as "this run does not exist" and stops polling; **six
management surfaces render admin chrome while identity is in flight** — and
forever if `me()` rejects, because none of those calls has a `.catch` (the correct
pattern exists one directory away); voice enrolment leaks the microphone on
unmount; and refusal `code`/`params` never cross the BFF, so consumers
string-match prose — and a **provider** refusal (an expired Google grant) is
reported to the user as a platform outage.

`core/vitest.config` includes `test/**/*.test.ts`. `core/test/e2e/schema-contract.ts`
is **not** a `.test.ts`, so vitest never collects it — and it carries four

## Part 3 — Twenty ways to make it faster

Ranked by impact ÷ effort. Backend items measured against the live database;
frontend items against the built output.

### The four that dominate

**1. Reading a transcript spends ~85% of its time on the permission check.**
The four transcript-related policies call `can_read_call(call_id)` **per row** —
1,324 segments means 1,324 permission lookups. It is `security definer` taking a
per-row argument, so Postgres can neither inline nor hoist it. Measured on the
live db: **296 ms → 42 ms** for the same rows with the rule expressed as a
semi-join (the auditor measured 745 → 47 on a colder cache). Corroboration:
`echo.org`, a **two-row table**, has been sequentially scanned **over a million
times**. Four one-line policy edits.
*Caveat:* my A/B ran at owner altitude, so it proves the cost, **not** that the
semi-join preserves RLS semantics for an app user. Prove equivalence first.

**2. three.js ships on 37 of 38 routes for an orb that renders on almost none.**
`560,777 B` — **49% of first-load JS** — pulled in because `PresenceDock` is
statically imported by the root layout. But `orbIsSilentOn` returns `true` for
`/assistant`, `/conversations`, `/workflows`, `/agents`, `/integrations`,
`/platform` and every auth route: the busiest screens pay ~141 KB gzipped for a
component they never render. There is exactly one importer of `three` in the repo.
One `next/dynamic` line.

**3. Every policy helper is PARALLEL UNSAFE.** `SECURITY DEFINER` defaults to
unsafe, so no query touching `call`, `call_part`, `transcript_segment`, `summary`,
`call_speaker` or `agent_message` can *ever* use a parallel plan. Two of the
helpers were explicitly marked safe, so the marking was known and simply not
applied to the hot six. `alter function … parallel safe` ×6.

**4. Missing indexes on the timer sweeps.** `echo.workflow` has **no index on
`trigger_event` at all** and is scanned on every product event; the mail,
calendar, wait and agent-rule sweeps all seq-scan. Five `create index concurrently`
statements (which need unwrapped migration files — 35 of the 129 self-wrap in
`begin/commit`).

### Backend

5. **`withIdentity` spends two round trips on preamble** before any query — measured 203 ms → 163 ms per transaction, and every database call in the product pays it.
6. **The ask path opens ~8 serial transactions (~40 round trips) before the first byte** — identity, last-seen, capability, preferred model, skill, two appends, context, run-begin, all awaited in sequence. Most are independent.
7. **`process_part` opens ~13 transactions for one part**, hitting the same row in three of them.
8. **`writeTranscript` inserts one row per segment** — 200 segments = 204 round trips where a multi-row insert is 5.
9. **The call list runs two correlated subqueries per row** — on a 6-row page that is 52% of the endpoint's I/O, and `can_read_call` fires again inside both.
10. **Idle worker polling: ~648k round trips a day doing nothing** — five handlers × their own transaction every 2 s, serial. One transaction plus idle backoff.
11. **The mail poller decrypts the OAuth token 6× per message and fetches the same Gmail message twice** (`format=metadata`, then `format=full`, which already contains the headers).
12. **The audit feed materialises all four sources for every page** — the keyset sits outside the `union all`, so page 1 reads every row of four tables to return 25.
13. **`agent_run.steps` is one awaited UPDATE per step, O(n²) bytes** — and the tool loop awaits it *before* returning the result to the model, so every tool call sits on the serial path.
14. **Five exactly-redundant indexes** on the hottest insert paths (`transcript_segment`, `call_part`, `agent_message`, `summary`, `call_speaker`), each duplicating a unique constraint, each with `idx_scan = 0`. Pure write amplification.
15. **`sessions.list` is unbounded with a correlated count per row**; `directory.list` runs the same correlated subquery twice per row; `purge` never batches (`batchSize` is a type field nobody reads, so 500 calls = 500 transactions).

### Frontend

16. **`/api/me` is fetched twice on every page load** — 25 callers correctly collapse through the promise cache, but `identityState()` calls the same endpoint raw, from a `PresenceDock` effect registered above its early return. Two lines.
17. **`Intl.DateTimeFormat` is constructed three times per rendered date** — a 10-row table is ~30 constructions per render, and these tables re-render on every keystroke of their search boxes. A module-level cache; ~8 lines.
18. **492 KB of unsubset TTF fonts** (Next does not convert to WOFF2) and a **517 KB PNG rendered at 24×24** — whose dark twin is 2400×2400 in 88 KB, so the light file is six times larger at half the resolution. Plus a full-bleed watermark served raw through CSS `url()`, bypassing the image optimizer.
19. **Every streaming token re-parses every message in the thread** — a global regex sweep plus `JSON.parse` per message, per delta, at 10–30 deltas/second. Streaming cost scales with thread length.
20. **The whole call list is fetched on a call's detail page** for a five-item sidebar that returns `[]` immediately when the call has no tags; **`/settings` statically imports all seven panes to render one**; the recorder and voice engines (~54 KB) load on every route; a bare URL costs **two redirects** before any HTML.

## Part 4 — Skeletons

**Zero `loading.tsx` files. Zero skeletons. Zero spinners.** All eight
`animate-pulse` uses are live-activity dots, never loading placeholders.

Of 30 async screens: **24 render blank while loading, and six of those actively
lie** —

| Screen | What it shows while loading |
|---|---|
| `/workflows/[handle]` | **"not found"** |
| `/workflows/runs/[id]` | **"run missing"** |
| `/integrations/[slug]` | **"detail missing"** |
| `/settings` → general | **"—"** for the workspace name |
| `/settings` → sign-in methods | claims **both providers enabled** |
| `/assistant` | the **new-chat greeting** while `?c=` is still loading |

The `T[] | null` convention (null = not fetched) is applied correctly and
consistently across 14+ sites — it simply resolves to `null` instead of a
placeholder. That makes the insertion point obvious and cheap:

1. One `scaffold/Skeleton.tsx` — a token-styled pulse box honouring
   `prefers-reduced-motion`.
2. **Widen `DataTable`'s `rows` to `T[] | null`** and render skeleton rows inside
   the real `<thead>`, so column widths hold and nothing reflows when data lands.
   This one change covers **ten screens** whose call sites already read
   `{x === null ? null : <DataTable/>}` — and it makes them simpler, not more complex.
3. One `app/[locale]/loading.tsx` rendering shell chrome + a body skeleton. Bonus:
   with zero `loading.tsx` today, Next's `<Link>` prefetch has nothing to warm for
   dynamic routes — adding one turns prefetch back on.
4. Fix the six liars: they are all one `=== null` branch away from honest.

## Part 5 — What to do first

**Today, before anything else** — three one-line fixes and one guard:

1. S1: refuse a foreign `actor_id` on key mint.
